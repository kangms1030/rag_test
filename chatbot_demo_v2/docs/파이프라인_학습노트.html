회색 박스에는 노드가 아닌 것이 섞여 있습니다

05scenario_matcher결정론 · 임베딩+리랭커

질문이 236행 FAQ(모범 질답) 중 하나와 같은 뜻인지 점수로 판정합니다. 생성 LLM은 쓰지 않습니다.

정규화 질문 → ① 정확 일치(비용 0) → ② 임베딩 코사인 top-10 회수 → ③ 크로스인코더 재점수 → ④ best / second / margin 계산
판정조건다음
exact정규화 문자열 완전 일치FAQ 즉답
acceptbest ≥ 0.80 그리고 margin ≥ 0.30FAQ 즉답
reject_ambiguous점수는 높은데 1·2위가 붙어 있음되묻기 후보
reject_low_scorebest < 0.80되묻기 후보 또는 RAG
왜 margin이 핵심인가

크로스인코더 점수는 0과 1로 몰려서 best만으로는 모호한 질문과 정답 매칭이 구분되지 않습니다 (“비밀번호를 바꾸고 싶어요” = 0.971). 골든셋 실측에서 모호 표본의 margin 최대값이 0.272였기에 0.30을 자동채택 문턱으로 잡았습니다.

실패 시
임베딩 파일이 없거나 백엔드가 죽으면 조용히 문자 유사도로 폴백하고 임계값도 스케일에 맞춰 함께 교체 → 결정론 경로가 죽지 않음
06route_decider노드 · 분기

4개 경로 중 하나를 고르는 파이프라인의 분수령입니다.

순위조건경로
1버튼 입력scenario_answer
2매칭 exact 또는 acceptscenario_answer
3애매 매칭 · best ≥ 0.35clarify_node
4회색지대 · best ≥ 0.35clarify_node
5그 외rag3x_answer
3번과 4번의 차이가 이번 개선의 핵심

3번(애매) = 후보 1·2위 점수가 붙어 있다 → 예전부터 있던 되묻기.

4번(회색지대) = 자동채택엔 못 미치지만 완전 무관도 아닌 구간 → 2026-07-27 신설. 이전에는 이 구간이 전부 RAG로 직행해 한 가지 해석만 골라 답했습니다. 발단 질문 “학교에서 새로운 ap를 설치하고 싶어”(best 0.386)가 정확히 여기입니다.

07clarify_nodeHITL · 실행이 멈추는 유일한 노드

상위 후보 2개를 보여주고 사용자가 고를 때까지 그래프를 정지시킵니다.

정지 단계

  1. 후보 2개 조회
  2. interrupt() 호출 → Pregel 루프가 여기서 멈추고 체크포인트에 상태를 저장
  3. API가 이를 감지해 “되묻기” 응답으로 후보 버튼을 내려보냄

재개 단계

  1. 사용자가 버튼 클릭 → 같은 스레드로 재개 명령 전송
  2. clarify_node가 처음부터 다시 실행됩니다
  3. 선택에 따라 FAQ 답변 또는 RAG로 동적 분기
면접·질의응답에서 좋은 디테일

interrupt() 이전 코드는 재개할 때 다시 실행됩니다. 그래서 이 노드에는 파일 쓰기나 카운터 증가 같은 부작용을 두면 안 됩니다. 코드 주석에도 명시돼 있습니다.

후보 선택
매칭 결과를 “확정(1.0)”으로 덮어쓰고 → scenario_answer
해당 없음
→ rag3x_answer
특이점
동적 분기라 이 노드에서 나가는 고정 엣지가 없습니다. 도식의 두 화살표는 런타임에 결정됩니다
08scenario_answer결정론

저장된 원문 답변을 그대로 꺼내옵니다. 시나리오 트리 또는 FAQ.

A · 버튼 경로

종단 노드면 정답 안내문 + 다음 버튼, 중간 노드면 질문 문구 + 선택지 버튼.

B · FAQ 경로

엑셀 모범답변 원문 그대로. 동시에 원본을 따로 보관해 두어 합성이 폐기될 때 되돌아갑니다.

근거 이미지
FAQ 경로는 근거 페이지 이미지를 최대 3장 복사해 함께 내려보냄 — LLM 0회, 파일 복사만
분기
FAQ면 → compose_answer / 시나리오 버튼이면 → final_formatter 직행
왜 버튼 답변은 합성하지 않나

버튼 종단 답변은 검증된 절차 안내문입니다. LLM이 다시 쓰면 문장은 부드러워지지만 절차가 흐려질 위험이 있어 원문을 유지합니다.

09rag3x_answer서브그래프 호출

어댑터를 통해 RAG 서브그래프 10노드를 통째로 실행하고 결과를 받습니다.

노드가 하는 일
① 질문 확정 — 재작성본 우선 → 후속질문 재작성 결과가 여기서 RAG로 전달됨
② 진행상황 writer를 잡아 콜백으로 어댑터에 전달(5절)
③ LangSmith 하위 run 생성

어댑터가 하는 일 — 도식의 “TTL 캐시 · 동시요청 락”

단계동작
① 캐시 조회질문을 정규화한 키로 조회. TTL 3600초, 최대 64건
② 캐시 히트락을 잡지 않고 즉시 반환 → 다른 사람이 RAG 처리 중이어도 429 없이 답변
③ 캐시 미스락을 기다리지 않고 시도 → 실패하면 HTTP 429
④ 정규화절대경로 제거 후 근거 이미지를 공개 URL로 사본
왜 기다리지 않고 거절하나

GPU 단일 처리라 큐잉하면 뒤 요청이 무한정 대기합니다. 기다리게 하느니 즉시 429로 거절하는 편이 데모에서 정직합니다.

10rag_result_evaluator노드 · 분기

RAG 결과를 채택 / 웹검색 / 보류 중 하나로 판정합니다.

조건결과
답변 있음 · 신뢰도 정상채택 → compose_answer
답변 있음 · 저신뢰채택 → compose_answer + 주의 문구 덧붙임
답변 없음 · 웹검색 활성→ web_search_answer
답변 없음 · 웹검색 비활성→ final_formatter (정중한 거절)
설계 원칙

“저신뢰”라고 답변을 폐기하지 않습니다. 답변이 실제로 있으면 제시하되 주의 문구만 덧붙입니다. v1에서 회피 판정 오탐 때문에 멀쩡한 답변이 통째로 버려졌던 사고에 대한 대응입니다.

11web_search_answer게이트 LLM 1회 + 웹검색 · 기본 OFF

내부 자료로 못 답한 ‘상담 범위 안’ 질문만 웹검색(Gemini + Google 검색 grounding)으로 보완하는 마지막 보루입니다.

진입점 2개 — 둘 다 “내부에서 답을 못 얻었다”는 신호
① rag_result_evaluator — RAG가 답변 자체를 못 만듦(빈 답)
② answer_grader — 답변은 나왔지만 UNRESOLVED. “제공된 자료에서 확인할 수 없습니다” 류 — 실사용의 대표 반려 형태
호출 전 통과해야 하는 조건
③ WEB_SEARCH_ENABLED=true
④ 도메인 게이트 = IN_DOMAIN — LLM 1회. ‘판정 불가’도 차단
⑤ 하루 호출 상한(WEB_SEARCH_DAILY_BUDGET) 이내
결과사용자에게 보이는 것
게이트 통과 · 검색 성공웹 답변 + 출처 링크 + “웹 검색 결과” 경고
OUT_OF_DOMAIN · 판정 불가검색 호출 없이 — 직전 답변이 있으면 그대로, 없으면 정중한 거절
검색 실패 · 출처 0건웹 답변 폐기 후 위와 동일
왜 직전 답변으로 되돌아가나

②경로로 들어오면 이미 저신뢰 RAG 답변이 손에 있습니다. 웹검색이 실패했다고 그 답변까지 버리면 사용자에겐 개선이 아니라 후퇴입니다. 웹검색은 덧붙이는 시도라 실패해도 손해가 없습니다.

API 키 — 유료 티어 전용

검색 grounding 은 결제가 활성화된 키에서만 동작합니다(무료 키는 429 RESOURCE_EXHAUSTED, 2026-08-03 실측). 그래서 웹검색만 WEB_SEARCH_GEMINI_API_KEY 를 쓰고, 없으면 GEMINI_API_KEY 로 폴백합니다. 지금 어느 키로 나가는지는 /api/health 의 web_search.key_source 로 확인합니다(키 값은 어디에도 노출하지 않습니다).

왜 게이트를 두었나

검색은 1회당 과금되고(월 5,000회 무료 후 $14/1,000회), 잡담·타분야 질문까지 웹에서 답하면 상담봇의 역할 경계가 무너집니다. 게이트는 검색을 타지 않는 텍스트 호출이라 사실상 무료이고, 하루 상한(WEB_SEARCH_DAILY_BUDGET, 기본 100회)을 넘으면 호출 자체를 하지 않습니다. 웹 답변을 채택할 때는 “내부 자료가 아닌 웹 검색 결과” 경고와 출처 링크를 함께 내려보냅니다.

12compose_answerLLM 1회 + 결정론 환각가드

원문이나 초안을 근거 기반 상담체로 재구성하고, 근거 밖 숫자가 생기면 합성 자체를 폐기합니다.

경로입력

RAG근거 페이지 텍스트 + 엔진 초안 + 질문 + 이력 요약

환각가드 — 이 노드의 진짜 핵심

합성문에 등장하는 3자리 이상 숫자와 코드를 근거와 문자열 대조합니다. 근거에 없는 값이 하나라도 나오면 합성을 버리고 원문으로 되돌립니다. LLM 판정이 아니라 문자열 대조라 속일 수 없습니다.

함정 — 실측으로 발견

검증 대상에 프롬프트 템플릿 원본도 포함시킵니다. 템플릿에는 우리가 박아 둔 지원센터 번호가 들어 있어서, 이걸 빼면 모델이 지시를 따라 그 번호를 안내했을 때 “근거 밖 수치”로 오탐해 정상 합성을 폐기해 버립니다.

출처 표기
RAG 경로는 [p53] 표기를 실제 근거와 대조 — 있는 쪽번호는 남기고 근거 이미지 링크로 렌더, 없는 쪽번호는 표기만 제거(문장은 남김)
실패 시
원문·초안 그대로 통과 — 답변은 반드시 나갑니다

4RAG 서브그래프 노드 10개

기존 RAG 엔진의 상태기계를 로직 수정 없이 노드로 재배치한 것입니다. 각 노드 본문은 기존 함수를 부르기만 합니다.

01prepare결정론

시작 시각, 제한시간, 그리고 세 종류의 사이클 예산을 세팅합니다.

세팅값
제한시간 240초 · CRAG 예산 1 · 답변 재생성 예산 1 · 경로 전환 예산 1
디버깅 일화 — 이야기로 쓰기 좋음

시작 시각을 상태 스키마에 선언하지 않으면 LangGraph가 조용히 버립니다. 그래서 총 소요시간이 계속 0.0으로 찍혔습니다. 선언된 키만 상태로 보존된다는 규칙을 보여주는 사례입니다.

02retrieve임베딩 + 리랭킹 · 생성 LLM 0회

질문으로 문서를 검색해 근거 페이지 최대 6장을 뽑습니다.

① 질문 임베딩 → ② 청크 검색 top-20 → ③ 크로스인코더 리랭킹
④ 무관 거절 게이트 — 최고점 < 0.1이면 즉시 “근거 없음”
⑤ 청크 점수를 페이지 단위로 집계해 상위 6페이지 전문 로드 → ⑥ 텍스트/이미지 경로 결정
도식에 없지만 중요한 안전가드

CRAG 재작성 후 2회차 검색에서는, 결과가 기존보다 나쁘면 원본 검색 결과를 유지합니다. 실측에서 재작성 질의가 정답 근거를 1위 → 7위로 떨어뜨린 적이 있습니다. 재작성이 항상 나은 게 아닙니다.

03grade_evidenceLLM 1회 · 2026-07-27 신설

검색된 페이지가 질문에 실제로 쓸모 있는지 3등급으로 판정합니다.

등급정의컨텍스트 투입량
primary이 근거만으로 답할 수 있다페이지 전문 (최대 4,000자)
supporting주제는 맞으나 핵심은 없다검색이 실제로 고른 청크만 (최대 800자)
irrelevant질문과 다른 주제제외
왜 만들었나 — 발표의 하이라이트

실측 트레이스에서 컨텍스트 5,949자 중 정답 근거는 9.6%, 무관한 3순위 페이지가 64.6%를 차지했습니다. 원인은 페이지 전문을 순위대로 이어붙이며 예산을 선착순 소진하는 구조였습니다.

더 중요한 발견 — 리랭커가 “AP 설치”라는 표현이 겹친다는 이유로 장애조치표를 1순위로 올렸는데, 파라미터 튜닝 3가지 모두 실측에서 악화였습니다. 의미 판정만이 유효했습니다.

비용 억제
페이지당 320자 발췌만 프롬프트에 투입
실패 시
전부 supporting → 기존과 유사한 동작으로 안전 저하. 읽지 못한 항목도 중립 등급으로(조용한 유실 방지)
—after_grade라우팅 함수 + 예산 배분

등급 결과로 분기하고, 등급별로 컨텍스트 예산을 배분합니다.

상태다음
살아남은 근거 있음answer_node
전부 무관 · CRAG 예산 있음crag_rewrite — 도식의 “근거 무관”
전부 무관 · 예산 없음finalize — 도식의 “근거 없음 → 보류”

예산 배분 규칙

primary : 페이지 전문, 장당 최대 4,000자 supporting: 장당 최대 800자, 매칭 청크 본문만 합계 = min(2000, max(400, primary글자수 × 0.5)) 한 문서가 supporting 예산의 60% 초과 불가 primary 0개 → 최상위 supporting을 승격 (그레이딩 오판 안전장치)
비율 상한이 필요한 이유

절대 상한만 두면 primary가 짧을 때(예: 574자) supporting 2,000자가 정답을 묻어버립니다. 근거 페이지를 3장→6장으로 넓힌 뒤 정답 근거 비중이 61% → 45%로 희석된 실측이 근거입니다.

04crag_rewrite사이클의 출발점 · LLM 1회

질문을 다시 써서 retrieve로 되돌아갑니다.

예산을 0으로 만드는 한 줄이 무한루프 방지 장치입니다.

실측 예 — 시연에서 나올 수 있음

“아이폰에 비해 갤럭시 기기들만 인터넷 속도가 느려…” (리랭크 0.054 < 0.1)
→ “갤럭시 스마트폰과 아이폰 간의 네트워크 속도 차이 원인 및 무선 인터넷 성능 최적화 방법”으로 재작성
→ 재검색해도 0.063 < 0.1 → 예산 소진 → 보류로 빠져나감. 무한루프가 아님을 증명한 기록입니다.

05answer_node결정론 흐름 · 생성 1회

검색 원본이 아니라 등급을 통과한 페이지로 답변을 생성합니다.

예산 적용
페이지 텍스트를 미리 잘라 두는 방식이라 기존 RAG 코드를 수정하지 않고도 예산 배분이 적용됩니다
경로 재확인
검색 1순위가 무관으로 걸러졌을 수 있으므로, 실제 답변 근거 기준으로 텍스트/이미지 경로를 다시 확인
06verify_node결정론 3종 + 조건부 LLM

답변이 근거와 맞는지 검증합니다. 결정론 신호 3종이 롤백 트리거가 됩니다.

신호판정 방법
회피(abstain)회피 문구가 있으면서 답변이 짧을 때만 회피로 판정
미지원 숫자답변의 3자리 이상 숫자·코드 중 근거에 없는 것 목록
전사 불일치이미지 경로 전용 — VLM 전사가 OCR 텍스트와 어긋나는 수치
이번 개선의 최대 발견 — 반드시 이야기할 것

회피 판정 문구에 “제공된 근거”가 들어 있어서 “제공된 근거에 따르면…”으로 시작하는 정상 답변이 회피로 오판됐습니다.

피해가 세 겹이었습니다 — ① 품질 검증이 통째로 스킵되고 ② 30.4초짜리 롤백이 발동한 뒤 같은 오탐으로 폐기되고 ③ 멀쩡한 답변에 “신뢰도가 낮습니다” 경고가 붙었습니다.

검색 알고리즘이 아니라 문자열 하나가 가장 큰 손실이었습니다.

LLM 절약
단일문서 · 높은 검색점수 · 숫자대조 통과 · 비회피 → groundedness LLM 호출 생략
최종 신뢰도
결정론 3종 통과 + groundedness 문제없음 → high / 회피 → abstain / 그 외 → low

10예상 질문 대응

“LangGraph를 왜 씁니까? if/else로도 되지 않나요?”

v1이 정확히 그 상태였습니다. v2에서 얻은 건 세 가지입니다.

  1. 사이클과 예산이 코드가 아니라 구조로 보인다 — 무한루프 방지가 그래프에 드러납니다
  2. interrupt() 없이는 되묻기 후 재개를 상태 저장·복원까지 전부 수작업으로 구현해야 합니다
  3. 노드 단위 관측과 스트리밍이 공짜로 따라옵니다

“LLM을 몇 번 부릅니까?”

경로호출 수
버튼0회
FAQ 정확일치합성 1 + 판정 1 = 2회 (토글 끄면 0회)
되묻기 (정지 시점까지)0회 — 후보 조회는 임베딩·리랭커라 생성 LLM을 안 씀
RAG 정상등급 1 + 답변 1 + 검증 0~1 + 합성 1 + 판정 1 ≈ 4~5회

“무한루프가 안 난다고 어떻게 보장하나요?”

되돌아가는 엣지는 CRAG 하나뿐이고, 진입 노드가 자기 예산을 0으로 만듭니다. 에스컬레이션도 같은 방식입니다. 롤백은 애초에 되돌아가지 않습니다. 여기에 제한시간 240초와 모델 호출 상한 5회가 이중 안전망으로 걸려 있습니다. 실측 트레이스에서 CRAG가 1회 돌고 두 번째에 보류로 빠져나가는 것을 확인했습니다.

“답변이 왜 느립니까?”

구간별로 나눠서 답할 수 있습니다 — 엔진 콜드로드(약 23초, 예열로 제거 가능) · 검색(2~5초) · 답변 생성 · 검증 LLM(외부 API 지연에 좌우, 실측에서 64초 걸린 적 있음). 그래서 조건부 생략과 타임아웃 25초를 도입했습니다.

“왜 근거 이미지를 보여주나요?”

텍스트 인용만으로는 사용자가 검증할 수 없습니다. 쪽번호 표기를 실제 근거와 대조해 정리하고 그 페이지 이미지를 함께 내려보내면 사용자가 원문에서 직접 확인할 수 있습니다. FAQ 경로도 같은 경험을 제공하며, 이쪽은 LLM 0회 · 파일 복사만으로 구현했습니다.

#이전 도식의 문제최종본에서발표에서 활용
8web_search_answer가 파란(결정론) 박스 “(기본 비활성)”이었다노란(LLM) 박스 + “① 도메인 게이트(LLM 1회) ② Gemini Grounding 검색 · 기본 OFF”“웹검색은 아무 때나 도는 게 아니라, 먼저 우리가 답할 질문인지를 판정합니다”
9출력 화살표가 1개라 게이트가 막는 경로가 보이지 않았다2갈래로 분리 — “웹 답변 + 출처” / “범위 밖 · 판정 불가 → 보류”이번 작업으로 새로 생긴 유일한 제어 흐름
10진입 라벨이 “웹검색”뿐이었고 SSE 단계·과금 설명이 없었다라벨 “무응답 ∧ 웹검색 ON”, SSE 목록에 web(게이트·검색) 추가, 하단에 발동 조건·과금 각주“도식만 보고 켜면 과금됩니다” 주의 환기
11웹검색 진입점이 rag_result_evaluator(무응답) 하나뿐이라 실제로는 발동하지 않았다 — 실사용 반려는 “자료에서 확인할 수 없습니다” 류 답변으로 나온다answer_grader 미해결 → 웹검색 엣지 추가(엣지 1개, 노드 수는 그대로)“웹검색은 RAG가 침묵할 때가 아니라, 답을 했는데 해결이 안 됐을 때 도는 게 핵심입니다”

오래된 문서 주의

발표에서 이 설명은 하지 마세요

기존 비교 문서에 “RAG 경로는 해결도 판정을 생략한다 — 내부 검증이 이미 판정하므로”라고 적혀 있는데, 현재 코드와 다릅니다.

2026-07-27 개선에서 그 근거였던 내부 검증이 회피 오탐으로 무력화 상태였음이 드러나 이 규칙을 폐기했습니다. 지금은 RAG 경로도 해결도를 판정하고, 미해결이면 신뢰도를 낮추고 경고를 붙입니다. 재시도만 하지 않습니다.

같은 문서의 실측 트레이스(2026-07-24)도 근거 등급 판정 신설 이전 기록이라 서브그래프가 9노드로 나옵니다. 최신 구조는 이 문서의 4절을 기준으로 하세요.
