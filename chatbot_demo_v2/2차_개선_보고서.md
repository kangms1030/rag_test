## 2. 왜 했나 — 진단

LangSmith 공개 트레이스 `8e0815cd`(질문: "학교에서 새로운 ap를 설치하고 싶어", **96.6초**)를
API 로 25개 run 전량 내려받아 분석했다.

### 구간별 시간

| 구간 | 시간 | 비고 |
|---|---|---|
| `rag3x.ask` 진입 → `rag_subgraph` 시작 | **23.2s** | 엔진 콜드로드 |
| `retrieve` | 5.1s | 임베딩 + 리랭킹(콜드) |
| `answer_node` | **35.2s** | Gemini 1콜 |
| `verify_node` | 0.00s | groundedness 미실행 |
| `rollback_top1` | **30.4s** | Gemini 1콜 — **결과 전량 폐기** |
| `compose_answer` | 2.3s | Gemini 1콜 |

### 원인 1 — 정상 답변을 abstain 으로 오판

[verify.py](ragcore/rag3/verify.py) 의 `_ABSTAIN_MARKERS` 에 `"제공된 근거"` 가 있었다. 원래는
[answer.py](ragcore/rag3/answer.py) 프롬프트가 지시한 회피 문구 `"제공된 근거에서 확인할 수 없습니다"`
를 잡으려던 것인데, 모델이 정상 답변을 `"제공된 근거에 따르면, …"` 으로 시작하면서 오탐했다.

피해가 세 겹이었다.
1. `verify_answer` 는 abstain 이면 groundedness LLM 검증을 **건너뛴다** → 품질 검증이 통째로 무력화
2. `after_verify` 가 `rollback_top1` 을 발동 → **30.4초 낭비**. 재생성 답변도 같은 문구로 시작해 또 오탐 → 폐기
3. `confidence="abstain"` → 멀쩡한 답변에 "신뢰도가 낮게 평가되었습니다" 경고

### 원인 2 — 검색 1순위가 오답인데 그대로 답변·롤백에 쓰임

| 순위 | 문서 / 페이지 | 점수 | 내용 |
|---|---|---|---|
| 1 | 무선랜 가이드라인 p22 | **0.5701** | "AP, SWIMS **장애** 관련 조치가이드" ← 무관 |
| 2 | 통합관제(사용자) p53 | 0.3508 | "9) 엑셀업로드 : 여러대의 AP장비를 한번에 추가" ← **정답 근거** |
| 3 | 무선랜 가이드라인 p16 | 0.2932 | SWIMS 실시간 조회 |

답변에 1순위 오염이 섞였다 — "AP 장비 교체 시에는 학교 자체적으로 설치하도록…" 은 p22 장애조치표
문장이다. 그리고 `rollback_top1` 이 `pages[:1]` = **오답 페이지 단독**으로 재생성해 구조적으로 더
나빠질 수밖에 없었다.

CRAG 재검색은 `answer_path == "none"`(리랭크 top < 0.1)일 때만 발동하므로 **"자신 있게 틀린"
검색은 절대 교정되지 않았다.**

### 원인 3 — 컨텍스트 예산이 관련도와 **반대로** 배분됨

모델에 들어간 컨텍스트 5,949자의 구성:

| 페이지 | 리랭크 점수 | 컨텍스트 비중 | 실제 관련성 |
|---|---|---|---|
| 무선랜 p22 | 0.5701 | 23.5% | 오답 |
| 통합관제 p53 | 0.3508 | **9.6%** | **정답 근거** |
| 무선랜 p16 | 0.2932 | **64.6%** | 무관(`<td>` 198셀) |

**정답 근거가 9.6%, 무관한 3순위가 64.6%.** 같은 문서 하나가 **90.1%** 를 독점했다.
`_format_context` 가 페이지 전문을 순위대로 이어붙이며 예산을 **선착순** 소진하기 때문이다.

여기에 구조적 낭비가 겹쳤다. 검색은 청크 단위(2,562청크)인데 답변은 페이지 전문으로 되돌린다.
p16 은 청크 5개 중 3개만 매칭됐는데 답변엔 미매칭 청크까지 전문이 들어갔다. 리랭커가 계산한
**청크별 점수는 `_retrieval_to_dict` 에서 통째로 버려지고** 있었다.

### 원인 4 — FAQ 매칭이 사실상 죽어 있었고, RAG 에는 품질 게이트가 없었음

- `scenario/matcher.py` 는 `rapidfuzz.fuzz.ratio` — **문자 편집 유사도**. 한국어 패러프레이즈는
  임계 0.90 을 절대 못 넘어 FAQ 236행이 도달 불가였다(이 질문의 최고 점수 0.4167).
- `answer_grader` 는 `route != "faq"` 면 즉시 반환했다. 주석은 "rag3x 내부 verify 가 판정하므로"
  였지만 그 verify 가 원인 1 로 무력화된 상태여서, **RAG 답변에는 어떤 의미 수준 검증도 없었다.**

## 3. 조사 과정 — 채택한 것과 **기각한 것** ★

> **이 절이 이 문서에서 가장 중요하다.** 유력해 보이는 개선이 실측에서 악화인 경우가 흔하다.
> 같은 시도를 반복하지 않도록 틀린 가설을 그대로 남긴다.

리랭커(bge-reranker-v2-m3)를 실제 GPU 에 올려 4가지를 검증했다. **3가지가 악화였다.**

| 시도 | 가설 | 실측 결과 |
|---|---|---|
| 카탈로그 프리픽스 제거 (`rerank_use_raw_text=true`) | 전 청크 공통 boilerplate 라 관련도를 희석할 것 | 정답 2위 → **3위 악화** |
| 리랭커 입력 절단 6,000자 → 1,200자 | 긴 표가 점수를 부풀릴 것 | 정답 2위 → **1위 개선** |
| 표를 행 단위로 분할(`chunk_table_split_chars` 축소) | 표의 한 행만 걸려도 표 전체가 상위로 오는 문제 해결 | 오답 조각이 0.5464 → **0.7297 악화** |
| CRAG 질의 재작성 | 키워드 중심으로 다시 쓰면 잘 걸릴 것 | 정답 1위 → **7위 악화** |

**표 행 분할이 특히 교훈적이다.** 쪼개니 "AP 장비 교체시 → 학교 자체 설치하라고 함" 행이 통짜
표보다 **더 높은** 점수를 받았다. 리랭커가 틀린 게 아니다 — 그 행은 문자 그대로 "AP 설치"에
관한 내용이고, **질문 자체가 진짜로 모호하다**(도입 신청 / 시스템 등록 / 물리 설치).

프리픽스는 청크의 41.3% 에서 본문보다 길고 색인 텍스트의 21.8% 를 차지하지만, 제거하면
오히려 나빠졌다 — 문서 단위 키워드가 dense 검색의 형제문서 변별에 기여하고 있었다.

### 결론 세 가지

1. **점수 기반 휴리스틱만으로는 부족하다.** 컨텍스트 배분 전략을 실측값으로 계산해 보니
   최고가 29.1%였고, 임계를 0.6 → 0.7 로 조금만 올리면 정답이 **통째로 사라졌다**(0%).
2. **의미 수준 판정만이 결정적이다**(9.9% → 100%).
3. **그러나 이진 컷은 위험하다.** 그레이딩이 정답을 잘못 떨어뜨리면 답변이 사라진다.
   그래서 관련/무관 이분법이 아니라 **3등급 차등 + 승격 안전장치**로 설계했다.

### 색인이 코드와 불일치했다 — 그리고 위생 필터도 한 번에 안 됐다

`ragdata/index/flat_chunk/.../docs.json` 을 직접 열어 확인한 것들:

- **코드-색인 불일치**: 178청크(7%)의 메타 `char_count`(1200)와 실제 색인 길이(8,448자)가 다르다.
  12,589자 청크를 현재 `chunking._split_by_maxlen` 에 넣으면 11조각(최대 1,199자)으로 정상 분할된다
  → **이전 규칙으로 만들어진 색인이 서빙되고 있었다.**
- **중복·노이즈**: 완전중복 138개(5.4%), 줄 반복률 50% 초과 65개(2.5%). 그런데 **이들이 가장 길다**
  (9,587자×5, 12,775자×10). 웹 UI 스크린샷 OCR 에서 브라우저 북마크바("M@gmail 변역 Perplexity")와
  887개 학교명 세로 나열이 그대로 색인됐다.
- **임베딩 잘림**: embeddinggemma 컨텍스트는 2,048토큰인데 151청크(5.9%)가 초과해
  **조용히 잘린 채** 색인돼 있었다. 잘렸다는 사실이 어디에도 남지 않았다.

**재색인 결과** (`scripts/reindex.py`, 643.5초):

| | 이전 | 이후 |
|---|---|---|
| 청크 수 | 2,562 | **2,424** |
| 최장 청크 | 12,775자 | 8,666자 |
| 임베딩 컨텍스트 초과 | 151개 | 124개 |
| 제거·압축 | — | 중복 138 · 반복줄 65 · **273,428자 절약** |

원본(`test_3/사전데이터`)의 파일 수·크기를 재색인 전후로 대조해 **훼손 없음**을 확인했다.

**그런데 여기서 끝이 아니었다.** 재색인된 색인을 다시 열어보니 **8,666자짜리 동일 내용 청크가
5개** 남아 있었다. 1차 필터가 두 가지를 놓쳤다.

1. 원문이 **1~2자씩 달라** 완전 해시 매칭을 빠져나갔다(MinerU 가 같은 페이지를 여러 번 뽑는다)
   → `near_dup_key`(길이 + 앞 400자 해시)로 근사 중복 판정을 추가
2. 반복 텍스트가 줄바꿈이 아니라 `" · "` 로 이어져 있어 **줄 기반 검출이 실패**했다
   ("이용명: 사업자주 및 사업자주 및 사업자주 …")
   → `collapse_inline_repeats()` 추가. 표 HTML 은 제외한다 — `<tr>` 반복은 정상 데이터다

보강 필터를 현재 색인에 재적용해 검증했다: **근사중복 12개 추가 제거, 62,879자 추가 절약**
(2,424 → 2,400). 이 보강은 **다음 재색인 때 반영**되며, 현재 서빙 색인은 1차 필터 기준이다.

> 데이터 위생도 한 번에 끝나지 않는다. 필터를 만들고 → 돌리고 → **결과를 다시 열어보는**
> 과정이 필요했다. 첫 필터만 믿고 넘어갔으면 43K자 노이즈가 그대로 남았을 것이다.

### FAQ 매칭 — 의미 유사도로 바꾸니 0/10 → 9/10

문자 유사도로는 패러프레이즈 10문항 중 **0개**가 정답 FAQ 를 찾았다. 임베딩 + 리랭커로 바꾸니
**9개**가 정답을 1위로 찾았다.

| 표본 | best(중앙) | margin(중앙 / 최대) |
|---|---|---|
| faq_paraphrase | 0.957 | 0.342 |
| ambiguous | 0.780 | 0.053 / **0.272** |
| rag | 0.004 | 0.002 / 0.484 |
| out_of_scope | 0.001 | 0.001 / **0.003** |

크로스인코더 점수는 0/1 로 몰려 **best 만으로는 모호 질문과 정답 매칭이 구분되지 않는다**
("비밀번호를 바꾸고 싶어요" best 0.971). **margin(1·2위 차)이 핵심 판별자**다 — 모호 질문은
최대 0.272 라 margin 0.30 문턱에서 걸린다.

되묻기 하한은 처음 0.05 로 잡았다가 **명확한 RAG 질문이 되묻기로 새는 것**을 발견해
(rag_01 0.087 · rag_07 0.184 · rag_04 0.326) **0.40** 으로 올렸다.

### 신규 그래프 노드 — `grade_evidence`

RAG 서브그래프가 9노드 → **10노드**가 됐다. `retrieve` 와 `answer_node` 사이에서 회수된 페이지를
LLM 1회로 3등급 판정한다.

| 등급 | 뜻 | 컨텍스트 대우 |
|---|---|---|
| `primary` | 이 근거만으로 답할 수 있음 | 페이지 전문(장당 4,000자) |
| `supporting` | 주제는 맞으나 핵심은 없음 | 매칭 청크만, 장당 800자 |
| `irrelevant` | 질문과 다른 상황 | 제외 |

- `primary` 0개여도 버리지 않고 **최상위 `supporting` 을 승격**한다.
- 전부 `irrelevant` 면 CRAG 재질의 → **CRAG 가 "점수가 바닥일 때"가 아니라 "의미상 근거가
  없을 때" 발동**하게 된다.
- 파싱 실패 항목은 `supporting` 으로 유지 — 판정 실패가 근거 유실로 이어지지 않게.

### 신규 관측 필드

`evidence_grades`(페이지별 등급) · `context_pages_used`(실제 투입 글자수·등급·승격 여부) ·
`citations`(검증된 인용 쪽번호) · `metrics.gemini_tokens_think`(사고 토큰).

## 9. 다시 손댈 때 알아야 할 것

`최종_구축_보고서.md §7` 의 8개 항목에 이어지는 추가분이다.

1. **골든셋 없이 검색 파라미터를 바꾸지 말 것.** §3 이 그 근거다.
2. **`grade_evidence` 는 `deps.prompts` 가 있어야 동작**한다. `SubgraphRagAdapter` 가 자체
   `PromptLoader` 를 만들어 `RagDeps(prompts=...)` 로 주입한다. 없으면 전부 `supporting` 으로
   폴백해 조용히 예산 배분만 적용된다.
3. **`RagState` 에 선언하지 않은 키는 LangGraph 가 조용히 버린다.** `started_ts` 가 그래서
   유실됐고 `timings.total` 이 항상 0.0 이었다. 노드가 새 키를 반환하면 `state.py` 에 반드시 추가.
4. **FAQ 매칭 임계는 스케일 의존적**이다. semantic(0.80/0.30/0.40)과 fuzz(0.90/0.05/0.75)는
   호환되지 않는다. 폴백 시 매처가 임계를 되돌리고 `MatchResult.scale` 로 알리며,
   `decide_route` 가 그 값으로 되묻기 하한을 고른다.
5. **FAQ 를 수정하면 `build_faq_embeddings.py` 재실행.** 안 하면 옛 임베딩으로 매칭한다.
6. **재색인은 `reindex.py` 로만.** `index_new` 빌드 → 골든셋 검증 → `--promote`(rename 2회).
   `--rollback` 으로 즉시 복귀. 원본(`test_3/사전데이터`)은 읽기 전용이며 파일 수·크기를 대조한다.
7. **`ragdata/` 와 `.env` 는 git 에 없다.** `.env` 는 유일본. 복원은 `_backup/RESTORE.md`.
8. **평가 러너는 clarify 를 인터럽트로 감지**한다(`result["__interrupt__"]`). 되묻기 문항은
   최종 답변이 없으므로 `answer_len=0` 이 정상이다.
